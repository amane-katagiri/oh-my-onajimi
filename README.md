# oh-my-onajimi

AI が書いた日本語の記事を、特定の筆者の書き癖に少しだけ近づけるための道具です。

文章を上手にする道具ではありません。今のモデルは、何も指示しなくてもまともな日本語を書きます。足りないのは「この人ならこう書く」という細かい癖です。oh-my-onajimi は、その癖を筆者の過去の記事から数えて辞書にし、モデルが書いた文章のうち癖から外れた箇所だけを指摘します。

## 仕組み

```
 筆者の過去の記事 ─┐
                   ├─ 比べる ─→ 差が出た表記・頻度・装飾 ─→ 筆者の辞書
 同じ見出しで      │   (onajimi profile)                    (profile.yml)
 モデルに書かせた ─┘                                            │
 記事                                                           ▼
                        モデルの下書き ─→ onajimi lint ─→ 指摘された箇所だけ直す ─→ onajimi guard
                                          (textlint)       (1 回だけ)              (数値と否定が
                                                                                  変わっていないか)
```

1. **比べる。** 筆者の記事と、同じタイトル・見出し構成でモデルに素で書かせた記事を並べて、語の使い方の差を数えます。話題をそろえてあるので、出てくる差は話題ではなく書きぶりの差です。
2. **辞書にする。** 差のうち、人が見て「これは癖だ」と判断したものだけを辞書にします。たとえば次のようなものです。
   - 表記の差：筆者は「全て」「分かる」と書き、モデルは「すべて」「わかる」と書く
   - 頻度の差：モデルは「を、」のように助詞のあとに読点を打つことが多い
   - 装飾の差：モデルは「- **ラベル**: 説明」型の箇条書きを使うが、筆者は使わない
3. **指摘する。** 辞書は textlint のルールになります。下書きにかけると、癖から外れた箇所が出ます。
4. **直させる。** モデルには、指摘された箇所だけを、文脈を見て直させます。指摘のない文は変えません。lint をもう一度かけて点数を追いかけることもしません。
5. **確かめる。** 直す前と後で、数値や否定（「〜ない」）が変わっていないかを `guard` で確かめます。

「AI っぽい語」の一覧を手で作る方法はとっていません。実際に比べてみると、そうした語は今のモデルの出力にはほとんど出てこなかったからです。差がはっきり出たのは、表記・頻度・装飾のほうでした（[notes/plan.md](notes/plan.md)）。

## まず lint を動かしてみる

このリポジトリには、作者（amane）のプロファイルが入っています。それを使って、下書きに lint をかけてみます。Node 22 以降が必要です。

```sh
npm ci
bin/onajimi build --author amane          # profile.yml から textlint の設定と辞書を作る
bin/onajimi lint --author amane draft.md  # 下書きを検査する
```

出力は 1 行に 1 件で、`行:列 ルール名 メッセージ` の形です。指摘がなければ何も出ません。

```
1:1 phrase-density 「〜し、」で文をつなぐのを減らす。文を切る。 1000字あたり 1.6（筆者はふつう 0.2、目安 1.2 以下）。
21:27 orthography すべて => 全て
87:199 orthography 気づ => 気付
```

ルール名ごとの意味は次のとおりです。

| ルール名 | 何を見ているか |
|---|---|
| `orthography` | 表記。筆者がふだん使う表記に置き換える候補 |
| `phrase-density` | 頻度。文書全体で、ある言い回しが筆者のふだんより多い（文書に 1 件、位置は 1:1） |
| `decoration-density` | 装飾。太字や箇条書きが多い、「**ラベル**:」型の箇条書きがある |
| `sentence-length`・`max-ten` | 1 文が長すぎる、読点が多すぎる |
| `model-leaning`・`author-leaning` | 語。筆者がほとんど使わない語、筆者なら別の言い方をする語（amane のプロファイルでは空） |

指摘は「直せ」ではなく「ここが筆者の癖から外れている」という目印です。直すかどうかは、文脈を見て決めます。

直したあとは、数値と否定が変わっていないかを確かめます。

```sh
bin/onajimi guard draft.md out.md         # 変わっていれば理由を出して 1 で終わる
```

## Claude Code で使う

このリポジトリは Claude Code のプラグインです。入れると、2 つのスキルが使えるようになります。

| スキル | 何をするか |
|---|---|
| `onajimi` | 記事を書き終えたあと、lint → 指摘箇所だけ直す → guard、を 1 回だけ行う |
| `onajimi-profile` | 新しい筆者のプロファイルを、人と相談しながら作る |

入れ方（このリポジトリのルートで実行します）:

```sh
npm ci
claude plugin marketplace add ./
claude plugin install onajimi@oh-my-onajimi
```

プラグインは、筆者のデータを Claude Code のプラグイン用データディレクトリ（`~/.claude/plugins/data/` の下）から読みます。このリポジトリにあるプロファイルを使うには、そこへ写します。

```sh
bin/onajimi import --root ~/.claude/plugins/data/onajimi-oh-my-onajimi --from . --author amane
```

データディレクトリの名前は `<プラグイン名>-<マーケットプレイス名>` です。ディレクトリはスキルを初めて使ったときに作られますが、上の `import` で先に作っても構いません。

あとは、Claude Code に記事を書いてもらうときに「onajimi で amane に寄せて仕上げて」のように頼みます。

## 自分のプロファイルを作る

自分の記事からプロファイルを作るときは、`onajimi-profile` スキルに頼むのがいちばん楽です。スキルは次の順に進め、決めどころでは必ず人に確認します。

1. **準備する。** `onajimi init` で設定のひな形を作り、記事の置き場所と、比較に使うモデル（Claude Code の `claude -p` や Gemini の API など）を書きます。
2. **見積もりを見る。** 比較用の記事を書かせるにはお金がかかります。`onajimi pipeline --estimate` が本数・時間・費用の目安を出すので、それを見てから `--yes` を付けて実行します。参考までに、記事 86 本を Opus に書かせたときは約 11 ドル、約 1.5 時間でした。
3. **候補を選ぶ。** 比べた結果は `review.md` にまとまります。候補には `O1`・`D3` のような番号が付いているので、採用するものを選んで `onajimi accept` で辞書に足します。
4. **確かめる。** 確認用に取っておいた記事に lint をかけ、筆者自身の文章に指摘が出すぎないかを見ます。直すのは 1 回だけにします。

スキルを使わずに手で進めることもできます。コマンドの流れは [docs/reference.md](docs/reference.md) にあります。

### 記事の分け方

筆者の記事は、日付の古い順に 4 つに分けて使います。役割を混ぜないことが大事です。

| 分け方 | 使いみち |
|---|---|
| プロファイル用 | モデルの記事と比べて、辞書の候補を出す |
| 確認用（dev） | 辞書が筆者自身の文章に誤って反応しないかを見る |
| テスト用（test） | 最後の評価に 1 回だけ使う。それまでは開かない |
| holdout | あとから増えた記事。テスト用に手を付けてしまったときの、まっさらな予備 |

テスト用の記事を見ながら辞書を調整すると、評価が甘くなります。テスト用は最後まで見ないでください。
